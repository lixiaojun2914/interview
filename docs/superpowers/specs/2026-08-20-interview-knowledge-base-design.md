# 面试复习知识库与 GitHub Pages 设计

## 1. 目标

将当前面试准备项目建设成一套可持续维护的结构化知识库：每个具体知识点均有独立页面，可由 MkDocs 构建成 HTML，并发布到 GitHub Pages。复习过程中产生的实验、错误和故障复盘独立沉淀，与相关知识点双向关联。

知识库面向 Cloud Native、Kubernetes Platform 与 AI Infra 研发岗位的投递前通用复习，不依赖特定职位描述。

## 2. 核心原则

- Markdown 是唯一内容源，HTML 是主要阅读界面。
- 一个具体知识点对应一个独立页面。
- 领域首页负责知识地图、推荐顺序和状态汇总，不承载全部正文。
- 内容按“原理 → 源码/代码 → 实验 → 故障现象 → 面试题 → 自己复述”形成闭环。
- 实验及其脚本自包含，错误和故障按统一证据链复盘。
- 先建立完整页面骨架，再按复习顺序逐页深入。
- 不用未经验证的泛化内容填满页面；未完成部分明确标记状态。

## 3. 信息架构

### 3.1 主体结构

左侧导航保留当前 00–19 的复习顺序。每个领域展开后包含：

1. 领域首页 `README.md`；
2. 该领域的具体知识点页面；
3. 指向相关实验、代码练习和故障复盘的链接。

新增两个全局栏目：

- `docs/labs/`：实验报告、脚本、配置和小型证据文件；
- `docs/retrospectives/`：错误、踩坑与故障复盘。

后续可增加 `docs/journal/` 复习日志。日志按时间记录阶段进展，使用博客式展示，但不替代结构化知识页面。第一阶段不创建空日志栏目；产生第一篇真实复习日志时再启用。

### 3.2 推荐目录

```text
docs/
├── 00-roadmap-progress/
├── 01-algorithm/
├── ...
├── 19-troubleshooting-performance/
├── labs/
│   └── <lab-name>/
│       ├── README.md
│       ├── scripts-or-configs
│       └── small-evidence-files
├── retrospectives/
│   └── <case-name>.md
├── journal/                 # 可选
│   ├── index.md
│   └── posts/
└── index.md
```

现有根目录 `labs/` 的说明迁移到 `docs/labs/`，后续不再维护两个实验目录。独立、需要完整构建环境的代码练习继续保留在根目录 `code/`，由知识点页面链接。

## 4. 页面规范

### 4.1 知识点页面

每个知识点页面统一包含：

1. 页面元信息：所属领域、学习状态、最后更新、前置知识；
2. 一句话定义；
3. 它解决什么问题；
4. 核心概念与关键术语；
5. 系统位置和上下游关系；
6. 执行流程、状态机或数据路径；
7. 实现原理、关键数据结构和源码入口；
8. 相关技术对比与工程取舍；
9. Kubernetes、Cloud Native 或 AI Infra 中的应用；
10. 实验与代码链接；
11. 常见故障、错误记录与排查入口；
12. 高频面试题及递进追问；
13. 一分钟与五分钟复述版本；
14. 参考资料及验证日期。

页面允许处于未开始、学习中、待复述、已掌握或需复习状态。骨架页只写已确认的信息和明确的待完善标识。

### 4.2 领域首页

领域 `README.md` 包含：

- 学习目标；
- 前置知识；
- 推荐复习顺序；
- 知识点状态表；
- 相关实验、故障复盘和代码入口；
- 本领域的整体复述检查清单。

### 4.3 实验页面

实验页面统一记录：

1. 实验目标；
2. 环境、版本与拓扑；
3. 前置条件；
4. 可重复执行的步骤；
5. 预期结果；
6. 实际结果与证据；
7. 故障注入与排查；
8. 清理和恢复步骤；
9. 结论与面试复述；
10. 关联知识点和复盘。

脚本、配置和小型证据文件与实验报告放在同一实验目录。大型抓包、二进制和敏感数据不进入仓库，只记录获取与复现方式。

### 4.4 错误与故障复盘

复盘页面统一记录：

1. 现象和影响；
2. 环境与触发条件；
3. 最初假设及其错误原因；
4. 调查过程与证据；
5. 根因；
6. 修复方案；
7. 验证结果；
8. 防止复发措施；
9. 可迁移的排障经验；
10. 关联知识点和实验。

## 5. 内容关联与进度

- 领域首页链接到知识点页。
- 知识点页链接到相关实验、复盘和代码练习。
- 实验与复盘页反向链接到相关知识点。
- 根目录 `progress.md` 继续作为总进度记录；HTML 中的 00 领域提供可浏览总览。
- 完成一次复习闭环时，同步更新知识点状态、领域状态表和总进度。
- 链接使用相对路径，确保本地预览与 GitHub Pages 子路径部署均可工作。

## 6. HTML 与 GitHub Pages

### 6.1 本地构建

继续使用 Material for MkDocs。保留全文搜索、代码高亮、Mermaid、明暗主题和移动端布局。`mkdocs build --strict` 是发布前的强制验证步骤。

### 6.2 自动发布

仓库使用 GitHub Actions：

1. 检出 Markdown 内容；
2. 安装锁定或明确版本范围的文档依赖；
3. 严格构建静态站点；
4. 上传构建产物；
5. 仅在构建成功后部署至 GitHub Pages。

发布目标为 `https://<user>.github.io/<repository>/`；若未来使用用户主页仓库或自定义域名，只调整站点 URL 和 Pages 设置，不改变内容结构。

### 6.3 知识库与博客的边界

00–19、实验和复盘属于结构化知识库，按主题组织。复习日志属于可选博客栏目，按日期组织，用于记录阶段性进展或学习过程。任何长期有效的知识都应回填到对应知识点、实验或复盘页面，不能只留在日志中。

## 7. 初始化策略

第一阶段为全部清单项创建独立页面和导航骨架，并升级领域首页。骨架包含统一结构、状态和关联入口，不批量生成未经验证的正文。

第二阶段按既定复习路线逐页完善：

- 算法每天持续；
- 第一主线依次推进 Linux Kernel、Linux Networking、Kubernetes Core、Kubernetes Development、Distributed Systems 和 AI Infra；
- 第二、第三梯队按依赖和面试价值穿插。

实验和复盘在真实复习过程中按需新增，不预造空案例。

## 8. 错误处理与维护约束

- 导航中出现缺失页面时，严格构建必须失败。
- 页面引用不存在的本地资源或相对链接时，应在验证阶段发现并修复。
- 实验不能复现时，保留实际结果和失败证据，不把预期结果写成实际结果。
- 外部资料必须标明来源和验证日期，优先使用官方文档、源码、论文和标准。
- 页面移动或改名时同步更新导航和所有反向链接。
- 不提交密钥、令牌、个人信息、内部地址或包含敏感数据的证据文件。

## 9. 验收标准

- 当前 README 中列出的每个具体知识点都有独立 Markdown 页面和对应 HTML 页面。
- 所有领域首页均提供推荐顺序和知识点状态表。
- 导航覆盖 00–19、实验记录和错误与故障复盘。
- 知识点、实验和复盘可以按约定双向跳转。
- 中文和英文核心术语可被站内搜索发现。
- `mkdocs build --strict` 成功，无导航遗漏和构建警告。
- 抽查桌面与窄屏页面，导航、表格、代码块和 Mermaid 可正常阅读。
- GitHub Actions 能在推送后构建并部署 GitHub Pages；失败构建不会覆盖已发布站点。

## 10. 当前实施边界

本轮实施包括信息架构、页面骨架、模板、导航、实验目录整合、复盘目录和 GitHub Pages 工作流。知识正文随后按复习过程逐页编写。复习日志栏目在产生第一篇真实日志时再加入导航和构建配置。

本轮不包括自定义后端、数据库、登录系统、评论系统、大型媒体托管或将全部骨架页自动填充为完整教程。
